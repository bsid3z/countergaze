# Guition JC3248W535EN

The 3.5" ESP32-S3 board this fork exists to support. It is **not** a CYD, does
not share a pin with one, and cannot run a CYD build.

| | |
|---|---|
| MCU | ESP32-S3-WROOM-1-N16R8 (Xtensa LX7, 16 MB flash, 8 MB OPI PSRAM) |
| Panel | 3.5", 320×480 native portrait, **AXS15231B over four-lane QSPI** |
| Touch | AXS15231B capacitive, I2C `0x3B` — same silicon as the display |
| Backlight | GPIO1 |
| SD | none usable |
| Build env | `jc3248` (console off), `jc3248-debug` (console on) |

## Why it needed a port at all

Three independent walls, each fatal on its own.

**1. Wrong chip family.** Every other board here is a classic ESP32 (Xtensa
LX6). This is an S3 (LX7). That alone is why the web flasher rejects it: the
manifests declare `"chipFamily": "ESP32"`, ESP Web Tools reads the chip ID and
refuses. Editing the manifest would not help — the binary behind it is LX6
machine code.

**2. TFT_eSPI cannot drive the panel.** Not a missing driver: a bus it does not
speak. Every other board hangs an SPI panel off TFT_eSPI, and the firmware has
~690 references to that library across ~97 files.

**3. Different touch controller,** on I2C rather than SPI.

## How it is wired together

The thing that made this tractable was already in the repo. The web emulator
has, for years, compiled the firmware's real UI sources against
`sim/TFT_eSPI.h` — a complete, portable, dependency-free reimplementation of
the TFT_eSPI/TFT_eSprite API that renders into an RGB565 buffer. It was a
preview tool with no way out to real glass.

This fork moved it to **`gfx/TFT_eSPI.h`** (one copy, shared by the emulator,
the host tests and this firmware build) and gave it that way out.

```
UI code (unchanged, ~97 files)
        │  draws into an 8bpp sprite, exactly as on every other board
        ▼
gfx/TFT_eSPI.h          the rasterizer — now the real driver here,
        │               not a preview. RGB565 buffer in PSRAM.
        ▼  pushSprite()
src/jc3248_panel.cpp    transpose into the canvas buffer, then flush
        ▼
Arduino_GFX             QSPI bus + AXS15231B power-on sequence ONLY.
        ▼               No drawing call is ever made through it.
        panel
```

`[env:jc3248]` sets `lib_ignore = TFT_eSPI` and puts `gfx/` on the include
path, so `#include <TFT_eSPI.h>` resolves to the rasterizer. Arduino_GFX is
pinned to **1.5.0** — 1.4.9+ includes `esp32-hal-periman.h`, which only exists
in Arduino core 3.x, and this project pins core 2.0.14 for unrelated reasons.

`SQW_HW_PANEL` is the flag that means "this rasterizer is the real driver".
It turns on the PSRAM allocator and the panel push, and by its absence keeps
`FastSprite` and `FramePush` out — both reach into the real TFT_eSPI's
internals, which are not here.

## Pinout

All confirmed working. None of it is guessed from a datasheet.

### Display — QSPI

| Signal | GPIO |
|---|---|
| CS | 45 |
| SCK | 47 |
| D0 | 21 |
| D1 | 48 |
| D2 | 40 |
| D3 | 39 |
| Backlight | 1 |

Panel reset is tied to the module's own — there is no GPIO to pulse.

### Touch — I2C, address `0x3B`

| Signal | GPIO |
|---|---|
| SDA | 4 |
| SCL | 8 |
| RST | 12 |
| INT | 11 |

Not a register map. The controller takes an 11-byte read command and answers
with a packet; see `src/cap_touch.cpp`. Coordinates come back in panel pixels
already, so the defaults need no calibration.

## Three dead ends, so nobody repeats them

**Pushing a sub-rectangle to the panel.** The obvious optimisation — only send
the region that changed — produces **a single column of lit pixels down the
left edge and nothing else**. This controller does not take partial window
writes. Everything goes through `Arduino_Canvas::flush()`, which writes the
whole buffer in one `draw16bitRGBBitmap`. If you ever see that one-pixel line,
this is what you did.

**Rotating the panel instead of the canvas.** `Arduino_AXS15231B::setRotation()`
writes MADCTL, and doing so makes the push a straight `memcpy` — it measured
181 ms → 48 ms. It also produces the same one-pixel line. **This panel ignores
MADCTL** and keeps taking its address window in native 320×480 portrait, so a
480-wide row is nonsense to it. `SQW_JC3248_PANEL_ROTATE` in
`src/jc3248_panel.cpp` documents this and stays `0`.

**Driving every candidate backlight pin.** Upstream's `setup()` writes GPIO 21,
27 and 32 high, because on a CYD the unused two are spare. On an S3, **GPIO26–32
are the internal flash and PSRAM lines**. Those two writes reconfigure the bus
the CPU is executing from: an interrupt-watchdog boot loop, every boot, before
`tft.init()` is ever reached. GPIO21 is also QSPI D0 here.

## USB serial is off by default

The S3's USB Serial/JTAG unit **resets the chip when a host opens the port** —
the boot log says `rst:0x15 (USB_UART_CHIP_RESET)`. Worse, with USB CDC enabled
and nothing draining the buffer, `Serial.printf` blocks and `setup()` never
finishes: the board runs fine on a PC and hangs on a power bank.

So `[env:jc3248]` sets `ARDUINO_USB_CDC_ON_BOOT=0`. Serial moves to UART0
(GPIO43/44). Flashing is unaffected — the ROM bootloader owns USB first. Build
`[env:jc3248-debug]` when you need the console, and accept the resets.

**Always press RESET after flashing.** esptool's post-flash reset fails on this
board, so it keeps running the previous image until something resets it. This
looked like a broken build twice during the port.

## Performance

480×320 landscape, measured on hardware via the `[frame]` console line:

| | first working build | now |
|---|---|---|
| Frame total | 407 ms (2 fps) | **137 ms (7 fps)** |
| Drawing (`post`) | 225 ms | 86 ms |
| Push | 181 ms | 54 ms |

Drawing came down by giving the rasterizer a `fillSpan` that writes a row
directly instead of one virtual `drawPixel` per pixel. That fix helps every
board and the emulator, not just this one.

The push came down by **tiling** the transpose. The canvas keeps its buffer in
the panel's portrait layout while the UI draws landscape, so every frame is a
transpose; done row-by-row it writes with a 640-byte stride and misses cache on
essentially every pixel. A 32×32 tile keeps both sides resident.

What is left is roughly one pass over 307 KB of PSRAM plus the QSPI transfer.

## Known rough edges

- **Battery voltage is not read at all.** This board has a divider on GPIO5
  (2:1), and nothing in the firmware looks at it — there is no battery UI on
  any board. Wiring one up is a feature, not a fix.
- **7 fps.** Fine for this UI, but `drawFastVLine` is still one virtual call
  per pixel and would benefit from the same treatment as `fillSpan`.
- **No SD.** `SdLog::begin()` returns early. The vendor pin list puts a card on
  10/11/12/13, which collides with the touch controller's reset and interrupt.
- **Rotation rebuilds the canvas.** Turning between portrait and landscape
  reallocates the 307 KB buffer. Rare, and the alternative is carrying both.
