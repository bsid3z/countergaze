===============================================================================
 SquachWatch — what it does, and technically what it detects
===============================================================================

 A standalone surveillance-device detector. It listens to 2.4 GHz WiFi and
 Bluetooth LE and identifies cameras, trackers, police equipment, attack
 tools and drones from their radio signatures.

 No PC, no app, no account, no cloud. Plug the board into USB and it works.

 SquachWatch is by skizzophrenic (Talking Sasquach):
   https://github.com/skizzophrenic/SquachWatch-CYD  .  talkingsasquach.com
 This repository is a fork that adds one board, the Guition JC3248W535EN.
 Licence: GPL-3.0.

 Everything below is read out of the firmware source (src/signatures.cpp,
 src/detection.cpp, src/remote_id.cpp, include/state.h), not from marketing.


===============================================================================
 PART ONE — HOW IT LISTENS
===============================================================================

 -----------------------------------------------------------------------------
 Bluetooth LE
 -----------------------------------------------------------------------------
 Library      NimBLE, compiled OBSERVER + BROADCASTER roles only.
              Central and peripheral roles are compiled OUT. The firmware
              cannot open an outbound connection and cannot accept one.
 Scan type    PASSIVE  (setActiveScan(false))
              It never sends a SCAN_REQ. It does not probe, wake, or
              identify itself to anything it detects. It only receives
              advertisements that were already being broadcast.
 Interval     100 (x0.625 ms = 62.5 ms)
 Window       75  (x0.625 ms = 46.9 ms)  -> ~75% duty cycle
 Duration     Indefinite (scan->start(0)), restarted on a watchdog
 Results      setMaxResults(0) — nothing is retained by the stack; every
              advertisement is handled in the callback and dropped

 What it reads out of each advertisement:
   - the advertiser's MAC (-> OUI lookup)
   - 16-bit service UUIDs (-> UUID table)
   - manufacturer data: the 16-bit company ID, then the payload
     (-> company-ID table, iBeacon check, Find My check)
   - the advertised device name (-> name matching)
   - RSSI (-> distance/signal meter, proximity logic)

 -----------------------------------------------------------------------------
 WiFi  (2.4 GHz only — the ESP32 has no 5 GHz radio)
 -----------------------------------------------------------------------------
 Mode         Promiscuous monitor mode (esp_wifi_set_promiscuous)
              with a promiscuous filter set for management frames.
 Channels     Hops 1 -> 13, dwelling ~300 ms per channel.
              Without hopping, the sniffer parks on one channel and misses
              everything transmitting elsewhere in the band.
 It NEVER associates, authenticates, or transmits in order to scan. The
 radio only joins a network when you explicitly ask for a firmware update.

 What it reads out of each frame:
   - source/BSSID MAC (-> OUI lookup)
   - SSID from beacons/probe responses (-> SSID prefix table)
   - frame subtype and rate (-> deauth flood detection)
   - the beacon's full tagged-parameter body (-> Pwnagotchi JSON)
   - encryption/auth advertised per BSSID (-> evil twin comparison)

 -----------------------------------------------------------------------------
 Bluetooth Classic
 -----------------------------------------------------------------------------
 Device-name matching against known modules, plus the Serial Port Profile
 UUID. This is how the card-skimmer modules are found — they are Classic
 SPP bridges, not BLE.


===============================================================================
 PART TWO — THE SEVEN DETECTION MECHANISMS
===============================================================================

 1. WIFI OUI PREFIX          77 entries. First 3 bytes of a MAC, matched
                             against the IEEE registry. Exact match.
 2. BLE 16-BIT SERVICE UUID  15 entries. Exact match.
 3. BLE COMPANY ID           7 entries. Bluetooth SIG assigned. Exact.
 4. WIFI SSID PREFIX         8 entries, case-insensitive prefix match.
 5. BT CLASSIC NAME          7 exact names + 5 substring matches.
 6. PAYLOAD DECODE           iBeacon header, Apple Find My, ASTM F3411
                             Remote ID, Pwnagotchi JSON. Structure is
                             parsed, not pattern-matched.
 7. BEHAVIOURAL / RATE       Deauth floods and evil twins. Nothing is
                             matched against a table — these are detected
                             from what the traffic is DOING.

 Confidence is graded PER SIGNATURE, not per type. Of the 77 OUI rows:
 33 High, 4 Medium, 40 Low. See docs/DETECTIONS.md for each one's
 provenance. Every hardware prefix was checked against the IEEE registry
 rather than copied from another detector.

 (The README says 76 rows and 32 High. It is one row out of date -- an ALPR
 prefix was added without updating the three numbers that describe the
 table. Counted from src/signatures.cpp, which is the only copy that can
 be wrong in a way that matters.)

 -----------------------------------------------------------------------------
 AIRTAG — Apple AirTag / Find My
 -----------------------------------------------------------------------------
 BLE company ID:  0x004C (Apple), then a Find My payload check on the
                  manufacturer data. Company ID alone is every Apple device
                  in the room; the payload check is what narrows it.

 -----------------------------------------------------------------------------
 SAMSUNG_TAG — Galaxy SmartTag / SmartTag+
 -----------------------------------------------------------------------------
 BLE service UUID: 0xFD5A  (Samsung's SIG-assigned discovery UUID)

 -----------------------------------------------------------------------------
 GOOGLE_TAG — Google Find My Device network
 -----------------------------------------------------------------------------
 BLE service UUID: 0xFEAA  (Eddystone, reused by the Find My Device network)
 Covers Chipolo, Pebblebee, Moto Tag. Best-effort: 0xFEAA is also plain
 Eddystone beacons.

 -----------------------------------------------------------------------------
 TILE — Tile trackers
 -----------------------------------------------------------------------------
 BLE service UUID: 0xFEED, 0xFEEC  (both SIG-assigned to Tile, Inc.)

 -----------------------------------------------------------------------------
 SKIMMER — Bluetooth card skimmers
 -----------------------------------------------------------------------------
 BT Classic name (exact): "HC-03", "HC-05", "HC-06", "RN42", "BT04-A"
 BLE/Classic service UUID: 0x1101  (Serial Port Profile)
 WiFi OUI (3):  20:13:00 (Linvor)  98:D3:00 (SPP module)  00:1A:7D (CSR)

 -----------------------------------------------------------------------------
 DRONE — Remote ID, and it is DECODED not just detected
 -----------------------------------------------------------------------------
 BLE service UUID: 0xFFFA (OpenDroneID)
 Then the ASTM F3411 message is parsed, and successive messages are MERGED
 into one picture of the aircraft:
   serial       up to 20 chars (ODID_ID_SIZE), the aircraft's ID
   uaType       PLANE QUAD HELI GYRO VTOL ORNITH GLIDER KITE FREEBAL
                CAPBAL AIRSHIP PARA
   lat / lon    the AIRCRAFT's position, degrees
   altM         geodetic altitude, metres
   opLat/opLon  the OPERATOR's position — where the pilot is standing
 The operator location comes from the System message. Merging matters:
 different fields arrive in different message types, so one advert alone is
 never the whole picture.

 -----------------------------------------------------------------------------
 IBEACON — Apple iBeacon proximity beacons  [OFF BY DEFAULT]
 -----------------------------------------------------------------------------
 Exact manufacturer-data header, at least 25 bytes:
   byte 0-1  4C 00     Apple, little endian
   byte 2    02        iBeacon type
   byte 3    15        length, 21
 Off by default because retail beacons are genuinely everywhere; turning
 them on is behind a screen that explains what you are about to see.

 -----------------------------------------------------------------------------
 HACKER — pentest and wireless-audit hardware
 -----------------------------------------------------------------------------
 Flipper Zero:
   BLE service UUID 0x3081, 0x3082, 0x3083  (one per case colour — three
                                             fixed values, so exact match)
   BLE company ID   0x0E29  (Flipper Devices Inc.)
                    NOTE: ESP32 Marauder and everything that copied it use
                    0x0FBA, which is Cosonic (headsets). That is wrong.
                    0x0E29 is checked against the SIG registry.
   WiFi OUI         0C:FA:22
   BT name contains "Flipper"
 WiFi Pineapple (Hak5):
   SSID prefix      "Pineapple_"   (documented default management AP)
   WiFi OUI         02:C0:CA, 02:13:37
 ESP8266/ESP32 deauthers (DSTIKE and clones):
   SSID prefix      "pwned"        (default SSID, password "deauther")
 Pwnagotchi:
   Its own beacon payload — a JSON blob stuffed into the tagged parameters
   of a beacon frame. Keyed on "pwnd_tot", which is what makes it a
   Pwnagotchi rather than any other beacon. Its name is read out too.

 DELIBERATELY NOT IN THIS BUCKET: bare Espressif and other generic silicon.
 A nyanBOX, an ESP32 Marauder and a SquachWatch are the same chip, and 16
 Espressif prefixes already sit under FLOCK. HACKER takes exact signatures
 only, which is what keeps it worth alerting on.

 -----------------------------------------------------------------------------
 DEAUTH — WiFi deauthentication / disassociation flood
 -----------------------------------------------------------------------------
 No signature at all. Rate-detected from behaviour:
   6 deauth/disassoc frames within a 3000 ms window
   then a 15000 ms cooldown before it can fire again
 This catches the attack, not the attacker's hardware — so it works against
 a tool that has never been seen before.

 -----------------------------------------------------------------------------
 EVILTWIN — rogue / spoofed access point
 -----------------------------------------------------------------------------
 Also behavioural: one SSID being beaconed from two different BSSIDs whose
 advertised encryption disagrees. A real AP and an impostor claiming the
 same network name cannot both be telling the truth about their security.

 -----------------------------------------------------------------------------
 UNKNOWN
 -----------------------------------------------------------------------------
 Everything else seen during a scan. Visible in RAW SCAN, not alerted on.


===============================================================================
 PART FOUR — WHAT IT DOES NOT DO
===============================================================================

 - No GPS. It never knows or records where you are.
 - It never joins a network in order to scan. Scanning is entirely passive.
 - It never sends a BLE scan request. It does not probe, wake or announce
   itself to anything it detects.
 - Central/peripheral BLE roles are compiled out — it cannot connect to
   anything, and nothing can connect to it.
 - 2.4 GHz only. A 5 GHz-only device is invisible to it.
 - No account, no telemetry, no cloud, no analytics.
 - WiFi is joined only for something you explicitly asked for: an update
   check or a firmware download.


===============================================================================
 PART FIVE — WHAT IT DOES WITH WHAT IT FINDS
===============================================================================

 MAIN / SCAN       Background, Squachy the mascot, live per-type counters.
                   Buttons: [ SCAN ]  [ LOG ]  [ DESK ]
 ALERT             Full-screen, in the detection's own colour: type, vendor,
                   the device's broadcast name, MAC, channel, signal meter,
                   instrument grid. Tap to dismiss or it clears after 60 s.
                   SNOOZE quiets one device until restart.
                   AUTO SNOOZE: five interruptions, then it must come closer.
 LOG               Rolling 200-entry detection log.
 DIARY             What the device has seen over time.
 RAW SCAN          Manual BLE/WiFi scanner — everything in range, not just
                   known signatures.
 HUNT              Live signal-strength gauge for a chosen target, to walk
                   it down.
 WATCH ALERT       A marked target comes back into range.
 BINGO             Detection bingo card.
 DETECTION FILTER  Per-type on/off.
 IGNORED DEVICES   Muted devices.
 DESK MODE         Desk clock: big seven-segment time, date, focus timer.
 SD LOGGING        With a card: squachwatch-<day>.log, CSV
                   ts,type,rssi,mac,channel,vendor,ssid
                   (Not on the Guition JC3248W535EN — no usable card slot.)


===============================================================================
 PART SIX — SQUACHMESH (BOARD TO BOARD)
===============================================================================

 Boards find and talk to each other over BLE advertisements — which is why
 the BROADCASTER role stays compiled in. Encrypted with a shared five-word
 phrase. No internet, no pairing server.

 DETECT            Other boards in range; their Squachy walks over to visit.
 MESSAGES          Short messages to your squad, red bubble with the
                   sender's name, read receipts, quick phrases or QWERTY.
 SQUAD             Everyone in range plus the inbox; members holding your
                   phrase read MEMBER.
 ADD TO SQUAD      Join without typing: both boards show the same four
                   digits, you confirm in person, the phrase goes over
                   sealed. Defeats a third board in the middle.
 PHRASE            Roll, show or type the five-word phrase.
 HUNT A MEMBER     Point the signal gauge at another board.
 Replay protection: counters persist across a crash, and every board checks
 its cipher against known test vectors at boot (MeshCrypto self-test).


===============================================================================
 PART SEVEN — SECURITY, UPDATES, THE REST
===============================================================================

 PIN LOCK          Locks the board. A locked board gives up neither its
                   phrase, nor its squad, nor its log.
 UPDATE CONSENT    A board obeys update nudges because it holds your
                   phrase; SECURITY can turn that off.
 WIFI UPDATE       Scan, join a saved network, download, install.
 BLUETOOTH UPDATE  From a browser over BLE.
 UPDATE CHECK      At boot, asks whether a newer release exists. Tells,
                   never installs. Can be turned off.
 UPDATE SQUAD      Tell every board in range to update, sealed with the
                   phrase.
 TWO APP SLOTS     1.92 MB each. An update lands in the spare one while the
                   current one runs; you can switch back.
 SIGNED PER BOARD  An image for a different display is refused rather than
                   installed as a white screen.
 Settings, PINs and mesh pairings survive updates — NVS is never erased.

 OUTFITS           14 costumes. Most earned by detection count; four hidden
                   behind things nobody tells you about.
 PET               Squachy has moods, reactions and a life.
 STATUS LIGHT      RGB LED with its own settings and a six-second TEST.
 CLOCK             Set by USB, or taken from the first squad member heard —
                   every squad hello carries the sender's clock and zone.
 POWER SAVER       Brightness, dimming, battery settings.
 BATTERY %         On the Guition JC3248W535EN only, the one board here with
                   a battery input. A percentage in the title bar, left of
                   the padlock and rotate icons: green, amber under 35%, red
                   under 15%, cyan while charging. Read off GPIO5 through the
                   board's 2:1 divider. Every other board has no battery
                   input and draws nothing.

                  pio run -e jc3248 -t upload

     nothing draining its buffer the firmware blocks in setup(). Build
     -e jc3248-debug for a console.


===============================================================================
 PART NINE — FOR DEVELOPERS
===============================================================================

 PC EMULATOR   sim/ compiles the real src/ against shims and renders actual
               frames; also runs in a browser via WebAssembly. Every
               screenshot in the docs is firmware output, not a mockup.
 HOST TESTS    make -C test — decoders, signature tables, and the
               emulator's fidelity to the display library.
               Linux/macOS: src/signatures.cpp uses strcasestr (glibc), and
               gfx/TFT_eSPI.h wants -D_USE_MATH_DEFINES on MinGW.
 CI            Every push: builds all boards, runs the tests, builds the
               emulator and renders a frame.
